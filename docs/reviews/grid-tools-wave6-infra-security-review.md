## Environment note (mechanism is valid here)
This repo's `aws-cdk-lib` exposes a first-class `Validations` API (`Validations.of(scope).addPlugins(...)` / `.acknowledge({id, reason})`), and `cdk-nag@3.0.2`'s `NagPack`/`AwsSolutionsChecks` **implements `IPolicyValidationPlugin`**. So `bin/grid-tools-app.ts` wiring `Validations.of(app).addPlugins(new AwsSolutionsChecks(...))` and the per-construct `Validations.of(x).acknowledge(...)` calls are the supported, native suppression path for these versions (the CDK docstring states acknowledgments are read by "downstream plugins (e.g. CDK Nag)"). This was checked against `node_modules` and confirmed by a passing synth that records the acknowledgments and surfaces no findings. Not a defect.

This is a documentation/expectation mismatch, not a security gap. **Fix (docs only):** enumerate the full acknowledged set in the ADR-6/§16.5 note so the "two ADR-tracked wildcards + N CDK-idiom/challenge-tier acknowledgments" split is explicit.

## Requirement-by-requirement verdict (all PASS)

1. **Least privilege / wildcards.** One dedicated role per Lambda (12 grid-tools functions → 12 distinct roles; `test_one_role_per_function`). `makeFunctionRole` avoids the AWS-managed basic-execution policy and scopes Logs to the function's own log group. Table/S3 grants use `grant*` helpers scoped to the resource ARN. **Only two `*`-resource action classes exist:** `geo-routes:CalculateRoutes` (ADR-10) and X-Ray `PutTraceSegments`/`PutTelemetryRecords` (no ARN to scope). Synthesized template confirms `geo-routes:CalculateRoutes` appears in **exactly one** policy, on the `plan-crew-route` role only. The absent CMK (ADR-6) is the service-managed-encryption deferral. No other broad grant slipped in (`test_wildcard_resources_are_only_the_two_documented`).
2. **SendTask isolation.** Template confirms `states:SendTask*` is held by **exactly** `WorkflowApprovalHandlerRole` and no other. `grantTaskResponse` is called only for the approval handler; the two proposal tools get `grantStartExecution` (start) but not task-response, and the approval handler is never granted `StartExecution` (start/resume split verified by `test_no_tool_role_can_start_and_resume`). The state-machine role holds no `events:PutEvents` — `grantPutEvents` is called only on the two proposal tools, the expirer and the approval handler; the machine's terminal states are `Succeed`/`Fail` and publish nothing (R13.5, §6.6).
3. **Sole-writer.** Only grid-tools function roles hold table write actions (`test_only_spec_functions_write_the_grid_tools_table`), and the two read-only tools (`trace_upstream_device`, `rank_restoration_jobs`) hold **no** write action. The IAM scoping — not just the test — enforces it: every write grant in the stack targets the `minnal-dev-grid-tools` table ARN and is attached to a grid-tools function role; the read-only tools receive only `GetItem`/`Query`/`BatchGetItem`. Within this standalone stack there is no external principal with table write. `DeleteItem` is confined to the Event_Ingestor (OKEY#/CREW# release) and the Work_Order_Expirer.
4. **Encryption / data safety.** Both DynamoDB tables: PITR on, SSE (AWS-managed) on; removal policy env-driven (`DESTROY` in `dev` as configured, `RETAIN` outside dev). Geometry S3 bucket: public access blocked, SSE, enforce-TLS (BucketPolicy present), versioned. Absent CMK is the documented ADR-6 challenge-tier suppression only.
5. **Gateway.** Inbound `CUSTOM_JWT` authorizer bound to the FAST Cognito issuer (user-pool id imported from SSM, not hard-coded). Per-function **reserved concurrency = 20** on all seven tools is the enforced DoS ceiling; the Gateway per-minute rate limit is recorded as a target tag and applied out-of-band (design A7 "rate limits fail open" documented in-code). Cedar policy engine associated in **`Mode: ENFORCE`**; `LOG_ONLY` is rejected by the config parser unless the env is on `policy_log_only_envs` (empty).
6. **Queues.** hazard/intake/DLQ all FIFO with content-based dedup, SSE-managed, enforce-SSL (3 QueuePolicies). hazard→Flood_Ingestor batch size 1; intake→Event_Ingestor batch size 10 with `reportBatchItemFailures: true`. hazard/intake redrive to the shared DLQ (`maxReceiveCount: 3`); the DLQ correctly has no redrive of its own.
7. **Secrets / hard-coding.** No secrets, no hard-coded ARNs (all built via `formatArn`/token literals), no literal account IDs in source (the `123456789012` in metadata is CDK's synth pseudo-account token; `017000801446` is the public AWS Powertools layer account). Gateway ARN is `{{GATEWAY_ARN}}`-substituted at synth via `Fn::Sub`. cdk-nag `AwsSolutionsChecks` runs on the stack with zero unsuppressed findings.
8. **Synth blocker.** The full-app synth failure (FAST's `CedarPolicyLambda` PythonFunction needing Docker/arm64 emulation) is pre-existing and owner-side, documented in `docs/plans/autopilot-state.md` and `docs/plans/grid-tools-build-notes.md`. It affects only the shared FAST stack; grid-tools' own tool Lambdas bundle locally with `uv` (no Docker) and the standalone `bin/grid-tools-app.ts` synthesizes cleanly with cdk-nag green. The blocker does not hide any grid-tools security gap — the entire grid-tools template is produced and asserted against.

## Conclusion
No High or Medium security findings. IAM least privilege, SendTask/StartExecution split, sole-writer scoping, encryption/data-safety, Gateway JWT + ENFORCE Cedar, FIFO/redrive queues, and secret hygiene all hold. The only items are documentation/expectation notes (full suppression set, deferred access logging) already tracked for pre-deploy hardening.

PASS
